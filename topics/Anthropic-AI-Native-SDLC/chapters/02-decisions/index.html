产品和研发在哪里作判断

本节要回答：有了 AI 参与，研发是否只要等到写代码时才出现？继续使用订单导出案例，看一条未解决的约束如何改变流程。

看清一次交接里的责任

原文边界。 产品负责人审核规格，政策冲突交给相应负责人；组织认定的较高风险事项要咨询技术负责人。实施前，工程师审阅 plan mode 产出的计划。图把这些判断的位置展开，未把技术评审画成所有改动都必须参加的一场会议。官方 Design 与 Build

产品负责人能够在准备好的环境中使用这些方法，并不表示前期不需要技术工作。平台或研发要先建立意图文件的存放位置、写权限和模板；政策由具名负责人维护。Skills、Hooks 等配置纳入版本控制，修改经过相应负责人审阅，让后续评审能够查到当时生效的规则。

让 AI 带回事实，再由人作取舍

案例讲解。 Agent 阅读代码后发现，订单查询接口已经限制了门店范围。这个发现可以减少研发寻找入口的时间，却还回答不了“客服是否应该跨店查看数据”。后一件事涉及业务职责和权限政策，代码现状只能提供事实，不能替组织作决定。

产品负责人先确认跨店导出是否确有业务需要。若只是单店核对，规格保持现有权限，研发确认复用方式即可。若需求变成跨店汇总，就要让相应负责人判断访问资格，并请技术负责人评估数据隔离会怎样变化。没有答案时，明确保留未决项，不能把 Agent 写出的完整段落当成已经批准的方案。

这里也存在一种简单情形：只修改导出按钮的文案，访问范围、接口和查询都不变。团队可以让日常负责人处理，不必为每次文案调整重复组织高风险评审。图中的风险分支用于找到需要更多判断的变化，不能把低风险当作免验证。

接受计划，究竟是在接受什么

假设计划写着“新增导出接口，前端接入，补充测试”。这还不足以让下一位工程师接手。我们继续追问：接口读取哪个数据源？权限在哪一层判断？测试怎样证明别家门店的数据不会混入？用户改动日期时，有没有复用旧结果的风险？

一个能执行的计划会把这些问题落到具体工作上。例如，先建立不同门店的测试数据，确认无权限请求会被拒绝；再实现服务端查询；最后接入按钮并验证导出字段。审计划的价值在于提前发现缺失的证明，避免等整套界面写好以后才发现底层权限方案不成立。

实施中发现原计划使用的接口无法满足需求，应当更新计划和关联决定。否则，评审者拿着旧计划，只能对一份从未真正执行过的方案作判断。计划是可以修订的工作记录，修订理由需要跟着结果留下来。

让情景变化，看看谁需要介入

打开交互式推演：文案调整、跨店导出、生产故障

切换情景时，观察三件事：哪些事实仍待确认，下一项行动由谁负责，行动前需要什么证据。该推演是教学设计，不会修改代码、调用模型或访问生产系统。

理解检查

假设 Agent 已经检查了所有接口，判断“跨店查询技术上可行”，产品也觉得功能有价值。这是否足以进入实施？还需要确认跨店访问是否获准，以及技术判断依赖哪些事实。技术上可做、业务值得做、组织允许做，分别回答不同问题。
