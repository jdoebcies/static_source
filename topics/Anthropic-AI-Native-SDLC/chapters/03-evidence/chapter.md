# 怎样判断代码已经可以交付

本节要回答：Agent 说“已经完成”，我们应该检查什么？继续看订单导出，从规则、测试走到合并和发布。

## 规则写下来以后，还要在哪里执行

![指导规则与执行边界各自怎样生效](../../images/07-controls.svg)

**原文要点。** `CLAUDE.md` 与 Skills 提供上下文和操作指导；Hooks、权限控制及流水线可以执行明确边界。写代码的 Agent 不能替自己的变更作最终批准。[官方 Build 与 Deploy](https://claude.com/blog/the-ai-native-sdlc-playbook#sd-s5)

**案例讲解。** 在说明里写“导出时不要泄漏其他门店订单”，能提醒 Agent 关注这个问题。服务端每次验证用户可访问的门店集合，才会在请求发生时真正限制访问。两者的失效方式不同：提醒可能被遗漏，程序也可能实现错。所以我们还要用测试观察限制是否有效。

对开发工具的限制同样如此。要求“修改完先跑测试”是工作规则；CI 拒绝合并失败的检查，是系统执行的条件。把这两类措施画在不同位置，能避免把提示词的存在误当成行为已经受到约束。

组织级规则还需覆盖执行环境。企业托管设置侧栏强调：个人不能扩大统一权限，工具限制、操作系统沙箱、网络与凭据控制要配合，不能因某一层失败而默认绕过。具体设置在[Deploy 完整译文](../../chinese/05-deploy/)核对。

## 从一次失败开始形成证据

![复现失败、修改实现与重新验证的回路](../../images/08-verification.svg)

假设我们发现门店 A 的操作员可以通过改请求参数导出门店 B 的订单。先固定这个请求与测试数据，让测试因为越权而失败。随后修改服务端的访问判断，使用相同的请求重跑。原请求被拒绝、正常请求仍成功，才能说明改动修复了目标行为且没有简单地关闭整个功能。

“全部测试通过”也要看测试究竟覆盖了什么。若只检查下载文件存在，它就不能证明访问隔离成立；若测试只是把期望值改成当前输出，失败消失也没有说明缺陷得到修复。测试变更有时合理，但应单独解释原因、检查新的期望是否仍符合需求。

涉及页面时，还要看到用户实际面对的状态：按钮是否重复提交、错误是否可理解、表格是否被遮挡。自动化测试提供一部分证据，截图和交互操作提供另一部分。任何一种检查的成功都只证明它实际覆盖的范围。

这里还要区分持续反馈与最终独立验证。开发时反复“改代码—跑检查—再修改”；验证子代理（verifier subagent）则在工作看似完成后，使用新上下文再检查一次。前者及时提供反馈，后者减少生成过程中的原有假设对最终判断的影响。独立检查仍需真实证据，也可能遗漏问题。

原文讨论自动接受日常编辑时，还有前提：规格清楚、影响范围小、测试覆盖已有行为，且保护措施已成熟。满足这些条件后可以减少逐次编辑确认，后续对意图、风险和发布权限的判断仍要保留。

## 谁看证据，谁有权批准

![生成、评审、合并之间的职责分离](../../images/09-review.svg)

在案例中，Agent 提交实现与测试结果；评审者核对字段范围、访问控制和异常行为，再由有权负责人决定是否合并。审查结果可以减少翻找代码的工作，但“没有发现问题”仍有检查范围。审查者需要知道它检查了哪份 diff、使用了哪些规则，未检查什么。

如果生成 Agent 同时能改掉保护规则并批准自己的 PR，流程图上再多一个“审核”框也无法形成独立判断。需要让批准路径与写入路径在权限上分开，并让实际合并依赖保护条件。

## 合并以后，仍有一个发布决定

![同一份变更怎样经过环境与发布条件](../../images/10-deployment.svg)

我们的导出功能先在隔离环境验证。如果页面正常，但真实数据规模下查询时间过长，就应继续处理，不能因为已经合并而跳过性能风险。假设准备发布时已经具备回退方案，发布负责人仍要知道本次影响哪些用户、如何识别异常、撤回会保留哪些数据。

生产操作的权限应与当前动作相称。能准备发布说明，不自动意味着能发布；能读取日志，也不自动意味着能执行回滚。这张图采用一套示例环境规则，团队需要据自己的环境风险确定条件。

## 理解检查

Agent 报告“测试全绿，评审没有发现问题”，但 PR 中同时删除了越权测试。你会怎么处理？查看测试删除理由，重建原失败情景并确认保护条件仍存在。若理由只是让检查通过，就要退回；若需求已正式改变，则核对批准后的新行为及其测试。
