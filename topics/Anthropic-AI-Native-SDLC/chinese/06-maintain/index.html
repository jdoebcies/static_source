06 Maintain：维护

循环闭合。触发器调用 Claude，无需人参与启动；它发现的问题以 intent.md 重新进入流水线。

维护与闭合循环

前面介绍了怎样把 Claude 接入 SDLC 各阶段，每个阶段的初始步骤都需要人启动。本阶段把重点转向 Claude 的自主运行，让循环闭合。

例如，持续运行的监测 Agent 可以在缺陷工单出现后创建 intent.md，推进需求、计划、开发实现、测试和评审。第 6 阶段“维护”以无界面方式运行，阶段之间设置独立置信度关口，由确定性检查或对抗式评审 Agent 判断：前一阶段的产出可以继续流转，还是应升级给人处理。

传统方式。 维护是被动响应的阶段。所有工单和事故都等待人采取行动、重新启动流程。凌晨 3 点的告警可能被漏看，工单可能一直留在待办中，复盘行动也可能因为下一起事故先发生而始终没有进入代码库。

AI 原生方式。 控制带越界、工单、频道消息或定时任务等触发条件直接调用 Claude，不必由人启动。Claude 诊断问题，仅沿着设有审批关口的路径行动，再把发现写为 intent.md，交给前述阶段处理。人负责分诊和评审，无需先把工作启动起来。

闭合循环

确定性脚本观察生产环境，指标越出控制带时调用 Claude。监测越界是理解自主循环的一个例子；本阶段末尾的 Claude Tag（公开测试版）部分，则说明其他渠道如何送入工作。

如何开始

前置条件： intent.md 为循环提供重新启动所需的结构化输出；Claude 加速的 PR 评审；作为行动边界的 Hooks；以及 CI/CD 的回滚路径，供最高自主等级调用。

基础设施： 检测脚本能查询的指标存储，例如 Prometheus、CI 系统 API 或类似系统；仓库只读权限；在 CI 中以非交互方式运行 Claude Code 的机制，或使用 Agent SDK 构建接收 webhook 的服务。

如何执行

  1. 服务负责人或平台工程师选择一个具有稳定滚动基线的指标，例如 CI 测试失败率、部署后 5xx 比例或 PR 周期时间。
  2. 编写检测脚本，通常使用滚动窗口中的均值与标准差，配合 Western Electric 等规则，使控制带既能发现缓慢漂移，也能发现突增。脚本纳入版本控制并做单元测试；检测完全确定，不使用模型。
  3. 在纳入版本控制的配置中定义响应等级，见下方 bands.yaml。1σ 时只记录日志；2σ 时以只读方式调用 Claude 诊断；3σ 时 Claude 可以行动，但只限于创建进入评审关口的 PR，或触发预先批准的操作手册（runbook）。
  4. 触发层可以是 GitHub 或 GitLab 定时工作流、既有监测系统的 webhook，或内网 Cron Job。Claude 无状态运行，可作为 CI runner 上的非交互步骤，或作为沙箱容器中的 Agent SDK 服务。部署和模型接入选项见 CI/CD 部分。因为运行无状态、非交互，循环无需人启动也能开始和结束。
  5. Agent 按第 1 阶段“计划”的格式把诊断写成 intent.md，包含异常及其证据、预期结果、受影响系统和未决问题。此后像其他发现一样进入流水线。
  6. 服务负责人或值班工程师对队列分诊，把面向产品的发现交给产品负责人。可以立即修复、排期或关闭；关闭记录用于调整控制带、减少噪声。
  7. 修复发布后，为事故增加一个 eval，防止同类问题再发生，见持续评估部分。

监测 CI 测试失败率的 bands.yaml 示例

metric: ci_test_failure_rate
baseline: rolling_30d
rules: western_electric
tiers:
  1sigma: { action: log }
  2sigma: { action: diagnose,
            tools: "Read,Grep,Bash(gh run view *)" }
  3sigma: { action: propose,
            routes: [pull_request, runbook:rollback-deploy] }

示例说明。 指标为 ci_test_failure_rate，采用滚动 30 天基线与 western_electric 规则。三个等级分别执行日志记录、限定工具的只读诊断，以及通过 PR 或预批准的回滚 runbook 提议行动。这里保留原文示例值。

治理方面的考虑

版本控制中的配置执行等级边界，权限与托管设置拒绝生产访问。调用、发现和分诊决定均带时间戳留档。服务负责人对发现分诊并批准；由此产生的改动进入正常 PR 评审；Agent 能触发的 runbook 则已预先获批。

如何衡量

指标类型 定义与取数方式
领先指标 从控制带越界到分诊队列出现 intent.md 的时间，与过去从事故发生到形成复盘行动的时间比较。检测脚本日志包含越界时间戳和事故等级。
滞后指标 发现最终形成已合并修复的比例，通过分诊队列与真实 PR 历史对应；另看同类事故的重复发生情况。修复持续向评估集添加案例后，重复事故应减少。

例子

  • CI 测试失败率越出 3σ 时，Agent 隔离不稳定测试或创建回退 PR，由评审关口决定。
  • 部署后 5xx 比例越出 3σ，且观测窗口内有部署发生时，Agent 触发现有回滚流水线。
  • PR 周期时间触发漂移规则时，Agent 为工程管理者撰写报告。这表明执行框架既能处理生产指标，也能处理流程指标。

检测保持确定性。指标越出控制带后才调用 Claude，响应等级决定它可以做什么。

定期扫描代码库

安全扫描反映某个时点、特定模型对某份代码库的判断，而代码和模型都会过时：代码每周变化，每一代模型也会发现前一代遗漏的漏洞。AI 原生做法是定期运行扫描，不依赖人启动，并让发现经过与其他代码变更相同的审批关口。

Claude Security 是定期扫描的托管形式。连接 GitHub 仓库后，扫描在 Anthropic 基础设施上使用 Claude Mythos 5 运行。每项发现在报告前都会验证，并附上置信度评级。建议补丁在网页版 Claude Code 中评审和应用。组织无需直接取得模型使用权限，就能获得扫描发现。

传统方式。 安全扫描是一项特定活动，通常在发布或审计前启动。报告进入追踪系统，团队手工消化待办，直到下一次扫描。在两次扫描之间编写的代码，只由 PR 评审所能发现的问题覆盖。

AI 原生方式。 对所有已连接的仓库，定期使用可用的最强模型扫描，发现经过验证后才交给人查看。处理方式与指标越出控制带相同：一个 PR 能解决的修复经过评审关口，更大的问题写为 intent.md。覆盖状态以最近一次扫描为准，而非最初一次。

如何开始

前置条件： 第 5 阶段的 PR 评审关口和作为审批关口的 Hooks，使发现像其他变更一样接受评审；对于一个 PR 无法解决的问题，使用第 1 阶段的 intent.md 格式。

基础设施： Claude Security 以公开测试版向 Claude Enterprise 组织提供。目标仓库必须位于云端 github.com，并安装 Anthropic GitHub App；启用网页版 Claude Code；开启 Extra Usage 并设置支出上限；运行扫描的人需要 premium 席位；管理员在 claude.ai/admin-settings/claude-code 启用功能。扫描按 Mythos 5 费率按量计费，因此支出上限应与仓库规模和数量相匹配。

如何执行

  1. 安全负责人连接仓库，并按仓库、服务或团队组织项目，使发现从一开始就有清楚的负责人。
  2. 对最重要的仓库进行首次完整扫描，包括已经被其他工具或早期模型扫描过的仓库。把首次扫描作为基线；它很可能在过去被认为没有问题的代码中发现新问题。
  3. 按项目设置周期。活跃开发的服务以每周一次作为起点比较合理；大型或混合仓库可将扫描限定到目录或分支。
  4. 结合置信度评级分诊。关闭发现时给出理由，使关闭决定留档，防止同一发现下一次又被当作新问题。
  5. 对范围明确的发现，在网页版 Claude Code 中打开建议补丁，评审后像其他变更一样进入 PR 关口。提出修复的 Agent 没有批准它的路径。
  6. 对超过一个补丁的事项，例如架构弱点或多个服务反复出现的模式，按第 1 阶段格式写成 intent.md，从 Plan 开始。
  7. 修复发布到生产后，为该漏洞类型编写一个 eval，加入持续评估部分的评估集，使引导 Agent 的配置从此接受这一类型问题的测试。
  8. 将发现导出为 CSV 或 Markdown，或使用 webhooks，让组织既有追踪和审计系统继续担当审计人员所预期的正式记录系统。

治理方面的考虑

扫描受组织的管理控制约束：连接哪些仓库、谁拥有扫描席位、支出上限多少，都集中设置。每项发现都有验证结果和置信度评级，每次关闭都有理由，因此扫描历史记录了发现什么、修复什么，以及明确接受了什么风险。

修复通过 PR 评审关口和分支保护进入生产，扫描本身不会直接发布。Claude Security 补充既有静态分析与依赖扫描：确定性检查仍在 CI 中运行，模型扫描则检查那些需要结合上下文、传统检查并非为之设计的漏洞。

如何衡量

指标类型 定义与取数方式
领先指标 已设置定期扫描的已连接仓库比例；以及从发现被报告，到补丁进入 PR 评审关口的时间，取自扫描历史和 PR 元数据。
滞后指标 比较定期扫描发现的漏洞，以及生产环境发现或外部报告的漏洞，数据来自事故追踪系统。另看经历多次扫描的仓库，每次扫描发现数量的变化趋势；随着修复和 eval 积累，数量应下降。

用 Claude Tag 参与值班

事故也会通过 Slack、Teams 等工作沟通工具到来。例如，事故频道晚上 10 点出现一条要求紧急修复的 Slack 消息，现在可以立即处理。Claude Tag（公开测试版，目前可在 Slack 中使用）以自己的身份成为频道成员，为每次新事故提供首轮响应。响应过程也进入循环，成为后续事故可以利用的记忆。

对话和组织知识保留在频道里，任何频道成员都可以指导和推进响应。团队成员能够实时检验假设、探索新选项和调查问题，频道历史增加了可审计性。通过 MCP，Claude 验证指标已经回到基线，并在讨论串中确认；随后把复盘写入纳入版本控制的经验文件，供未来调查阅读。

Claude Tag 接手的不只是事故。经 MCP 在工单中提及它，或在频道里向它提出请求，都按相同方式分诊。范围小、边界明确的修复以 PR 经过评审关口；更大的事项写为 intent.md，进入第 1 阶段“计划”。循环由此开始持续接收后续工作。参见 Claude Tag 在 Anthropic 如何承担 CI/CD 值班。
