第18章

边界剖析

上一章讨论把哪些东西隔开，本章继续问：隔开之后，两个组件怎样合作？边界可以藏在同一个可执行文件里，也可以表现为独立进程或网络服务。形态不同，通信代价不同；要保护的源代码依赖方向却可以保持一致。

一、原书回顾：边界怎样从代码延伸到服务

跨边界调用

运行时，一个边界内的函数调用另一边的函数，并把数据交给它，就是跨边界调用。但作者关心的不只是一次调用能否成功。某个模块的源码一变，其他模块是否必须跟着修改、重新编译或重新部署，才决定了这条边界能否限制变更的影响。

因此，边界承担的是针对变更的隔离作用。运行时两个组件仍然合作，源码却不必互相知道所有细节。接下来的几种边界，都是在不同部署条件下安排这种合作。

令人生畏的单体结构

最轻的边界没有独立进程或网络端口：组件在同一个进程、同一个地址空间中，仅在源码中划分职责和依赖。最终产物可能是静态链接的 C/C++ 程序、打包的 Java 可执行 JAR，或者 .NET 可执行程序。作者称它为单体结构，也把这种划分称为源码层次上的解耦。

部署时只看见一个文件，不会抹掉开发时的组件边界。不同团队仍可以分别开发、测试高层规则与低层细节。作者强调，多态使这种划分更容易维持：代码可以依赖一个稳定接口，由实际对象决定执行哪一种实现。他把大量使用函数指针的风险作为历史背景，这是作者对工程实践的判断，不是本章给出的测量结果。

先分清两种跨边界情形。

图18-1｜根据原书图18.1、18.2重绘。上半图中，低层客户端调用高层服务，调用与源码依赖同向；下半图只画源码依赖，高层客户端通过自己的接口调用低层实现。实际调用低层实现的方向由图下说明给出，不能把两种箭头当成一回事。

第一种情形是低层客户端调用高层服务。原图的 Client 调用 Service 的 f()，同时传递 Data。Service 和 Data 的定义都在高层一边，所以调用方知道被调用方的接口和数据结构，源码依赖也指向高层。这时，调用方向和源码依赖方向自然一致。

第二种情形是高层客户端需要低层服务。若直接引用低层实现，高层就会随实现变化。原书把 Service 接口和 Data 一起放到高层客户端一边；低层 ServiceImpl 实现这个接口，并使用高层定义的数据结构。高层 Client 的代码只提到 Service，运行时却能通过它调用 ServiceImpl。跨越边界的源码依赖全部指向高层，运行调用则从高层走向低层。

这里的数据归属也有意义。若只把接口移到高层，参数类型还定义在低层，高层仍需导入低层类型，隔离就没有完成。原图两次改变 Data 所在的一侧，正是在强调接口和数据结构必须共同检查。

单体结构中的跨边界交互通常就是普通函数调用，成本低，因而可以频繁调用。作者以整体编译、静态链接的典型方式说明它的交付特点：组件通常以源码参与最终构建。脚注补充，泛型、模板等静态多态有时也能管理单体内依赖，但不能据此获得动态多态在避免重新编译、重新部署方面的全部好处。

部署层次的组件

下一种边界把组件做成能够单独交付的单元。原书列举 DLL、JAR、Ruby Gem 和 UNIX 共享库等形式。部署者接收二进制或等价的可部署内容，无需在部署现场重新编译组件；整个系统仍可被收集成 WAR 或一个目录。

这种变化主要发生在交付方式上。组件仍可处于同一进程、同一地址空间，彼此使用普通函数调用。因此，源码依赖的管理方法与单体基本一致，通信也仍然廉价。动态链接或运行时加载可能付出一次性成本，不应把这个成本误算到每次函数调用上。脚注也限定：前述静态多态通常不适合承担这种部署解耦。

线程

线程管理程序何时执行、怎样被调度。一个线程可以始终在一个组件里工作，也可以调用多个组件的函数，所以线程本身既不是架构边界，也不是部署单元。

这段专门阻止一种混淆：给任务换个线程，只改变执行安排，不会自动消除源码依赖。单体和独立部署的组件都能使用多线程。

本地进程

本地进程带来了更明显的物理隔离。多个进程可以运行在同一台机器的处理器上，却有各自的地址空间；若要共享数据，需要使用专门的共享区域或进程通信机制。作者列举 socket 和操作系统提供的消息通信方式。

一个本地进程内部又可以是静态链接的单体，也可以由动态链接组件组成。把进程看成较大的组件后，内部的依赖仍须管理，进程之间的源码依赖也仍应从低层指向高层。高层源码不应写死低层进程的名字、物理地址或注册表键名。目标是使低层实现可以作为插件被接入，而不要求高层认识它的部署细节。

与函数调用相比，进程通信要经历系统调用、数据编码和解码，以及执行上下文切换。这些额外步骤使通信更贵，边界设计因而需要控制交互次数。

服务

服务进一步把位置独立性纳入设计。彼此通信的服务可以同机，也可以位于不同机器；它们按网络通信的条件来安排合作。不能因为现在部署在同一台机器，就让接口假设每次交互都像内存函数调用一样便宜。

作者以几十毫秒到数秒的往返时间说明网络延迟可能显著高于函数调用。这是本章用于解释设计取舍的量级描述，不是对任何现网接口的性能承诺。因此，服务边界应减少往返，并容忍高延迟。

方向规则仍然相同：低层服务应当能成为高层服务的插件，高层源码不应包含低层服务的 URI 等物理信息。某个地方当然需要知道地址，但把地址交给接入和配置代码处理，才能使高层规则保留独立性。

本章小结

一个系统通常会同时使用多种边界。服务可能由多个本地进程构成；进程内部又可能包含多个源码组件或动态链接组件。因此，设计者需要同时照顾低延迟、高频率的本地交互，以及高延迟、较少往返的远程交互。选择服务并不会取消内部边界的工作。

二、主题讲解：把“能替换实现”和“能分开部署”分别想清楚

从同一个借贷计算程序开始

以下是为讲解构造的假设案例。一个 Java 程序负责计算还款计划，并读取客户的信用结果。最初，计算代码直接创建某个信用查询客户端，还把服务器地址写在方法里。此时改地址、换供应方或替换通信方式，都可能改到计算源码。

先让计算一侧定义所需能力：给定客户标识，取得用于这次计算的信用结果。具体查询代码实现这个接口；装配程序创建实现，再交给计算对象。计算运行时仍会请求低层查询，但它在源码中只认识自己的接口。这个改变可在单个 JAR、单个线程中成立。

检验它时，可以用内存中的假实现返回信用结果，让计算测试不启动真实查询服务。测试能这样运行，是接口隔离有用的一项证据。它还不能证明真实网络连接、认证或协议兼容性正常，这些需要另行验证。

再决定是否值得拉开物理距离

图18-2｜依据本章三类通信机制整理。箭头表示一次交互要经过的额外步骤，不表示系统必须按这个次序升级。图不承诺具体性能数值。

信用查询实现如果仍放在同一进程，跨接口只需普通调用。若出于实际部署需要把它移到另一个本地进程，就要编码请求、跨进程传输，再解码结果。若移到网络服务，还得按照网络延迟安排调用方式。接口在语义上可以相近，通信条件已经改变。

例如，原来循环计算每期还款时反复读取同一份信用结果，在本地调用中可能尚可接受；变成远程请求后，往返会被循环次数放大。合理的改进是先确认业务是否允许在一次计算中使用同一份结果，再把它一次取回。若业务确实要求每次重新检查，就不能只为少调用而擅自缓存。边界改变通信成本，不会替我们决定业务需要的数据新鲜程度。

看一次修改会触及哪里

现在分三种变化检查设计。只改查询服务地址，应由配置和接入代码处理；更换查询供应方，应尽量只改接口实现和结果转换；改变“哪些信用条件允许计算”的业务规则，则应该修改负责这条规则的高层代码。三种变化落到不同位置，是划分边界的具体收益。

不过，如果新供应方返回的数据根本无法满足原接口承诺，业务确实可能需要调整。接口只能隔离被预先分开的变化，不能让语义发生变化后系统仍然完全不动。讨论边界时，把“实现换了”与“需要的业务能力换了”分开，才不会过度承诺可替换性。

最后再看线程：把信用查询放进线程池，或让计算与查询在两个线程执行，不会自动解决上述依赖和数据归属。线程解决执行安排；源码、部署、进程和服务边界分别解决不同层面的隔离。

自测：多了一个进程，边界就更好吗？

假设计算程序把信用查询拆成独立服务，却仍然直接导入供应方的响应类，并在计算循环里对每期还款发送一次请求。请分别判断源码隔离和通信设计。

核对思路：进程确实分开了，但供应方响应类仍把它的变化带入计算源码；接口及所需结果结构应由需要它的高层一侧定义。调用次数还要根据业务上是否需要重复查询来调整。不能仅凭“已拆成服务”判断边界质量，也不能仅凭调用次数多就随意省掉必要检查。
