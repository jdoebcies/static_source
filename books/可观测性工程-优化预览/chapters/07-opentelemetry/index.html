第7章

遵照OpenTelemetry的探针

本章要回答：怎样用OpenTelemetry生成可用的遥测，自动探针之外还需要补什么？

上一章手工生成ID、传上下文、计时再发送span。若每次更换分析产品都要重写这些探针，业务代码就与后端工具绑在一起。本章介绍OpenTelemetry（OTel）如何分开这两部分，并解释为什么自动探针得到调用图之后，仍需要业务开发者补充字段和工作阶段。

一、原书回顾：先获得调用骨架，再补业务含义

7.1 探针简介

埋点让运行中的代码产生遥测：发生了哪项工作、当时有什么属性、结果如何。作者把宽事件视为一种包含大量结构化字段的日志，把trace视为带有关联字段的一组事件。

过去的产品往往要求应用安装自己的库或代理，并按专有接口增加自定义探针。换后端就可能重复埋点，甚至同时运行两套测量逻辑。这是本章要减少的厂商锁定，而不是取消所有后端差异。（PDF 60）

7.2 开源探针标准

作者沿OpenTracing、OpenCensus到2019年合并为OpenTelemetry的历史，解释统一API和数据通道的动机：尽量保留应用端探针，用导出配置选择后端。

书中关于标准地位、支持语言和兼容性的判断属于成书时语境。理解其设计目的，不等于承诺任何语言版本、任何信号或任何产品都无需适配。本文保留组件和工作流程，用伪代码讲解，不把旧Go API当作当前SDK安装教程。（PDF 60—61）

7.3 使用基于代码的示例的探针

原书选择Go演示，目的是看见每段代码在做什么，不要求读者先成为Go开发者。其“OpenTelemetry概念速成”把职责拆成以下组件：

原书术语 在本章过程中的职责
API 应用调用的埋点接口，让业务代码表达开始工作、加属性、结束等动作
SDK 实现这些接口，管理记录、处理和导出等行为
tracer 创建与操作trace中的span；当前span通过上下文取得
meter 取得和使用指标测量接口
上下文传播 在进程内带着当前关联信息，在跨进程时编码与还原
exporter 将记录转换并发送到指定目标
OTLP OpenTelemetry Protocol，用于传输遥测的协议
Collector 独立进程，接收、处理并导出到一个或多个目标

API表达动作，exporter负责数据出口，Collector则是可选的进程外处理环节。它们不是八个必须在业务函数里逐个调用的步骤。（PDF 61—62）

7.3.1 自动化探针

HTTP包装器、gRPC拦截器等在框架处理请求前后调用OTel，读取远端上下文、创建span、记录属性及耗时，再结束span。原书Go代码用 otelhttp.NewHandler 包装HTTP处理器，gRPC示例注册一元和流式拦截器；Java、.NET等语言还可用运行时Agent支持部分框架。

它们快速提供“谁调用谁”的骨架，但前提是所用框架及调用边界获得支持，并完成正确配置。自动探针不会凭空知道客户分片、业务分支或应用中某段计算的意义。（PDF 62—63）

7.3.2 增加自定义探针

链路span的开始和结束。 原书从当前上下文创建一个有名字的子span，函数退出时结束。上下文既可能泛指业务发生的条件，也可能特指OTel的关联对象；这里传入的是后者。创建子span后，后续工作应使用它的上下文，否则新增阶段可能没有成为预期的父。（PDF 63—64）

给事件增加宽的字段。 通过当前上下文拿到活跃span，增加整数或字符串属性。原书示例设置 http.code 与 app.user，分别表达状态码与当前用户。这些是该示例的字段名；业务字段要有稳定意义，当前HTTP语义约定则按所用版本核对。添加属性保留的是这个工作单元的条件，无需为每个属性再造一个span。（PDF 64）

记录process-wide指标。 原书另示范用meter周期性记录运行中的goroutine数量，并附应用和容器属性。这一数值不属于某一请求；预定义维度上的精确非采样计数也是作者承认的指标用途。与此同时，作者明确偏向把请求相关的值留在宽事件中，认为过度依赖预聚合程序指标会限制后续调查。例外和取舍应一起保留。（PDF 64—65）

7.3.3 发送探针数据到后端系统

产生数据后有两条路径：SDK通过exporter直接发送到分析后端，或先发送到Collector，再处理和路由。原书OTLP示例在启动阶段创建导出器与TracerProvider，配置服务身份和批量发送；另一例子同时注册两个exporter，让旧工具继续工作，也能试用新工具。

作者建议优先用OTLP的gRPC exporter连接支持它的后端或Collector；若不采用Collector，且目标后端不支持OTLP或有其他自定义导出需求，再配置对应exporter。这个选择条件来自原书，不是所有当前部署必须遵守的唯一方案。

两路出口不等于每份数据天然一致。采样、过滤、映射和发送失败都可能造成差别。原书具体端口、API、默认假设和 AlwaysSample 配置仅用于当时的示例；实际应用要核对运行配置，不能将其提升为所有OTel部署的默认行为。（PDF 65—66）

7.4 结论

OTel降低应用探针对后端的绑定，自动探针帮助建立起点，自定义span与属性提供业务解释。开发者仍要决定记录什么、哪个工作阶段值得单独观察，以及数据怎样导出。第8、9章继续判断这些数据能支持什么样的调查。（PDF 66）

二、主题讲解：一段慢函数怎样出现在trace里

自动探针已经记录HTTP，但120毫秒仍是一整块

以下为补充的假设案例：HTTP服务的自动span总耗时120毫秒，但不知道授权、姓名查询之外的本地工作占多少。代码里有一段 parseProfile，我们希望知道它是否慢，以及慢是否与输入大小相关。

无需再复制一个相同的HTTP span。给解析阶段增加内部子span，并把输入规模作为属性：

// 启动时完成一次配置，具体SDK API依语言与版本而定
provider = configureSdk(service="profile-api", exporter=otlpExporter)
tracer = provider.getTracer("profile-parser")

// 自动探针已建立HTTP span，并把它放进requestContext
childContext, parseSpan = tracer.startSpan(requestContext, "parseProfile")
try:
    parseSpan.setAttribute("profile.input_bytes", inputByteCount)
    profile = parseProfile(input)
    parseSpan.setAttribute("profile.record_count", profile.recordCount)
catch error:
    parseSpan.recordError(error)
    raise error
finally:
    parseSpan.end()

这里创建的子上下文供解析阶段内部的后续埋点继续使用。若解析函数又调用带探针的组件，应把 childContext 传进去或在该语言的作用域中设为当前；只创建变量但继续用旧上下文，后续span仍可能挂在HTTP父上。

记录出现后，下一步看什么

假设本次输出包含：

名称 父span 开始/持续毫秒 关键属性
HTTP GET /profile 根 0 / 120 service=profile-api
parseProfile HTTP span 20 / 75 input_bytes=800000，record_count=6000

这次解析占据了HTTP时间的大部分，但单条trace仍不能证明“输入大必然慢”。下一步取相同版本、相同路由的其他请求，按输入大小比较解析时长。若补一个 parser.variant 字段，还能在发布后比较新旧解析实现；第11章会把这一过程接到开发反馈。

如果后端没有出现 parseProfile，按数据经过的顺序检查：这段代码是否执行，是否存在有效父上下文，span是否结束，是否被采样保留，SDK是否导出，Collector或后端是否收到。不能把“应用启动没有报错”当成端到端验收。

自动与手动传播的边界

在已支持并配置好的HTTP或gRPC路径上，库可以代劳注入与提取。自定义队列、未覆盖的客户端、线程切换或异步回调不一定继承当前上下文；是否自动处理要看实际库和框架。OTel提供Propagators API处理需要手动传播的场景。官方上下文传播说明

判定方法保持具体：发一条带已知业务关联值的请求，读回子span，核对Trace ID、直接Parent ID和预期工作名。若换成异步路径才断开，就沿交接处检查上下文捕获与恢复，而不是在所有服务里盲目再加一套ID。

事件字段、内部span与进程指标怎样选

“解析了多少条记录”是解析工作的属性，可留在该span；“解析阶段花了多长时间”值得建立有起止的内部span；“整个进程当前有多少goroutine”属于进程范围测量，用meter周期采集。这三种对象回答不同问题，不应为了统一形式全部变成指标，或给每个简单字段单独建立span。

检验理解

情形：HTTP自动探针正常。你新建了子span P，但数据库调用仍收到旧的HTTP上下文。后端数据库span与P是兄弟。为何如此，怎样验证修正？

核对：当前上下文决定创建时的父。应在本例数据库调用处使用P的子上下文或相应作用域，再读回实际Parent ID；只改span名称不能改变关系。是否应归P，还要确认数据库调用本就属于P所表示的工作。

情形：将同一数据发到两个后端，A有100条，B有70条。能否断言OTel不支持迁移？

核对：不能。先统一时间窗和采样条件，核对两条出口的过滤、发送失败、接收延迟及查询口径。标准化降低耦合，迁移仍要用同一批数据实际验证。
