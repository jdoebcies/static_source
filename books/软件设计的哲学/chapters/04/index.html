第4章

模块应该深

如果每次使用一个模块都要先弄懂它的内部细节，系统分成许多类之后，人仍然要面对大部分复杂性。本章提出“深模块”：让使用者通过较简单的接口，获得较多功能，内部复杂工作由模块承担。

一、原书回顾：接口的成本，能否换来足够的功能

4.1 模块化设计

模块化设计把系统分成相对独立的类、子系统或服务。作者先提出理想情形：如果模块完全独立，开发者一次只需理解其中一个，整体复杂度就只取决于最难的模块。但真实模块必须合作，因此总会互相了解一些信息。方法参数变化会影响调用者，某个操作要求先调用另一个操作，也会产生依赖关系。

管理这种依赖，需要把模块分为接口和实现。接口包括别人正确使用模块必须知道的所有内容；实现是完成接口所承诺功能的代码。模块开发者需要理解自己的接口和实现，以及自己调用的其他模块的接口，通常不必理解那些模块的内部实现。

平衡树说明了这个分工。使用者通过插入、删除和查找来操作数据，插入时提供键和值即可；如何遍历树、调整节点以保持平衡，可以留在内部。这里的模块不专指类，方法、函数、系统调用和通过 HTTP 请求访问的服务，都有相应的接口与实现。

接口远比实现简单的模块有两项好处：给使用者增加的理解成本较少；只要内部变更保持接口承诺，外部就可能不受影响。模块化的价值来自这种隔离，而非模块数量本身。

4.2 接口包含哪些内容？

接口有正式部分和非正式部分。正式部分明确写在代码中，例如参数名称与类型、返回类型、异常信息、公有方法和变量；其中一些可由编程语言检查。参数数量或类型不匹配，通常就能被发现。

非正式部分描述行为和使用约束。例如某函数会删除参数所指的文件，或一个方法必须在另一个方法之后调用。只要正确使用必须知道，这些信息就已经属于接口，不能因为没有写进签名就忽略。作者认为，对多数接口而言，这部分往往更大、更复杂。明确写出它，能帮助使用者知道自己需要掌握什么，减少“不知道未知”。

正文强调注释承担非正式说明，语言本身无法保证说明完整、正确。不过，第 52 页脚注补充：一些主要用于研究的语言，可以用规范语言正式描述方法或函数的整体行为，并自动检查规范与实现是否匹配。作者承认它们可能取代部分非正式接口，但个人认为用英语描述接口，对开发者可能更直观易懂。这是原书保留的技术例外与个人判断，不能删成“行为绝不可能由工具检查”。

4.3 抽象

抽象是对实体的简化，省略不重要的细节。模块接口提供的，就是其功能的简化视图。这里最难判断的是“不重要”：对当前使用者正确完成任务没有影响的细节，才能省略。

抽象有两种失败方式。暴露不需要的细节，会增加认知负担；删掉使用者真正需要的信息，则会让接口看起来简单，实际无法被正确使用。后一种称为错误的抽象。设计要寻找能减少必需信息的结构，同时保留仍然必要的说明。

文件系统的例子把两者分开。文件放在哪个物理块，通常可隐藏，只要性能满足需要；但有些数据库应用必须知道数据何时真正写入持久存储，以判断崩溃后能否保存。内部缓存、延迟写入与刷新规则因此不能一概从接口中删掉。对一种用途无关的细节，可能对另一种用途很重要。

微波炉和汽车是日常类比：使用者通过少量控制操作获得功能，无需理解微波产生、电源管理、制动控制等全部机制。类比说明简化视图的价值，没有取消使用设备时仍须掌握的约束。

4.4 深模块

图4-1｜按原书图4.1重绘。矩形顶边长度表示接口复杂程度，面积表示提供的功能；这是一种定性比较，不是按代码行数计算的几何指标。

作者把功能强大、接口简单的模块称为深模块。从成本收益看，功能是收益，接口是它给系统其他部分带来的理解成本。接口增加只有换来足够多的功能或隔离作用才值得，并非接口越多越好。

原书用 UNIX 文件 I/O 举例，列出五个基本系统调用。open 接收文件路径和打开选项，返回标识已打开文件的整数文件描述符；read 和 write 在文件与应用程序内存之间传输数据；close 结束访问；lseek 调整当前位置以支持随机访问。通常的顺序访问不需要调用者主动管理偏移位置。

这些基本操作背后需要解决：磁盘文件布局、目录与路径查找、权限检查、中断及后台工作的分配、多文件访问调度、内存缓存，以及不同存储设备的整合。作者指出，实现可以变得庞大并长期演变，而使用者仍主要通过这组基本操作访问文件。此处是在说明原书选取的基本接口，不意味着整个文件系统只有五个接口，也不取代上一节关于持久性规则必须可见的限定。

另一个例子是 Go、Java 等语言的垃圾回收。作者从普通应用程序显式释放对象的角度，说它在幕后回收不用的内存，甚至减少了程序员必须调用的释放接口。其实现很复杂，但常见代码不必理解这些机制。这里“没有接口”的措辞针对普通对象释放操作，不能外推为整个运行时没有任何配置或观察接口。

4.5 浅模块

浅模块的接口相对复杂，却没有隐藏多少功能。原书认为，普通链表的插入删除只需少量代码，其接口和实现的理解成本可能相近，因此属于较浅的模块。作者同时承认，浅模块有时难以避免，也仍然有用；“浅”是提醒评估收益与接口成本。

他接着给出课程项目的极端例子，下面按 PDF 第 57 页恢复排版：

private void addNullValueForAttribute(String attribute) {
    data.put(attribute, null);
}

这个方法只是把 data.put(attribute, null) 换成一个更长的名字。调用者仍可能必须知道属性存入 data，接口没有给出更简洁的理解方式；认真写文档可能比实现本身更长。新增一个需要学习和查找的方法，却没有相应隐藏复杂性，是作者批评它的理由。

本节的“警示信号：浅模块”概括这一点：若学习接口的成本抵消了不必理解内部的收益，模块对降低复杂性帮助有限。小模块较容易出现这种问题，但短方法并不自动等于坏方法。

4.6 类炎

作者用“类炎”描述把“类应该小”推到极端的设计倾向：每个类尽量少做事，更多功能一律通过更多类实现。他也反对机械地按固定行数拆方法，书中举出的阈值甚至可低至 10 行。

结果可能是每个局部都简单，整体却要理解大量接口、管理更多对象并重复引用它们。问题出在判断只看单个类有多短，没有把跨类协作的成本计入。深度讨论因此需要同时观察模块外部，而不能只检查一个源文件。

4.7 示例：Java和UNIX I/O

作者用一段从文件读取序列化对象的 Java 构造过程说明常见路径上的接口成本。以下是原书跨第 58—59 页的片段，展示对象组装，不是完整资源管理示例：

FileInputStream fileStream = new FileInputStream(fileName);
BufferedInputStream bufferedStream = new BufferedInputStream(fileStream);
ObjectInputStream objectStream = new ObjectInputStream(bufferedStream);

在原例中，第一个对象提供基本文件输入，第二个加入缓冲，第三个提供对象读取。组装完成后的业务读取通过 objectStream 进行，但调用者事先必须知道并创建另外两层。作者尤其批评“显式添加缓冲”：忘记这一层，就不能获得该层提供的缓冲行为，在原书讨论的访问方式下可能使 I/O 很慢。

反方理由是缓冲应该可选，并非所有人需要。作者接受保留选择，但认为常见情况应尽可能简单：若绝大多数用途需要缓冲，就应默认提供；少数不需要者再通过单独构造方式或关闭、替换缓冲的操作调整。这样普通调用者无须先学习罕见选项。

他以 UNIX 的顺序访问对照：顺序读取是默认行为，随机访问者使用 lseek；只顺序读的人不必理解随机定位接口。这说明一个接口即使有很多特性，只要常用任务仅需掌握其中少数部分，其日常复杂度仍可能较低。这是作者对原书示例的评价，不是在罗列所有 Java 版本可用的文件 API，也没有比较不同语言库的全部能力。

4.8 结论

接口与实现分离，才有可能把实现复杂性留在模块内。设计类、函数或服务时，应争取让常见场景使用简单接口，同时获得有分量的功能。这样，使用者需要接触的复杂性才会减少。

二、主题讲解：一个方法，也可能有很大的接口

先问调用者必须知道什么

以下是本文假设的报表导出模块。它只有一个 export 操作，看起来接口很小。但调用者必须先创建临时文件、选择字符编码、准备表头映射、调用导出，再关闭资源并删除临时文件。若这些条件缺一不可，它们都属于接口成本。数公有方法，只能看到其中一小部分。

尝试把调用者的知识逐项写出，会发现其中几项并不服务于“导出这份报表”的业务判断。例如临时文件何时创建和清理，可以由导出模块自己负责。如果这些步骤在模块内完成，调用者只需提供报表数据及确实需要选择的输出形式，同一个操作就隐藏了更多工作。

隐藏工作，还要保留成功的含义

现在模块对外只返回“导出成功”。但是成功指生成了内存内容，还是文件已经可读取？文件由调用者保管多久？失败时会不会留下部分结果？如果调用者需要据此给用户一个可下载文件，这些信息不能因为接口追求简短而消失。

深模块承担了临时文件管理等内部工作，同时清楚说明调用者真正需要的结果和约束。错误抽象则把必要条件藏起来，让调用者先凭猜测使用，出错后再阅读实现。两者表面上都可能只有一个方法，但实际使用成本不同。

再检查扩展是否拖累常见使用

假设绝大多数报表使用同一编码，少量对接才需要另一编码。可以考虑给普通导出使用合适的默认值，把特殊配置放在单独入口。这样需要特殊行为的人仍能表达需求，普通调用者则不用学习无关参数。这对应原书常见情况优先的原则。

默认值必须有真实使用前提。如果各种编码需求同样常见，或选错会改变数据含义，就不能隐瞒这个选择。类似地，把所有导出相关工作塞进一个持续膨胀的大类，也不保证更深；若调用者必须理解更多无关规则，接口成本仍会上升。评估深度要同时看提供了什么功能、隐藏了什么细节、留下了哪些必须理解的条件。

检验理解：一行包装有什么价值

比较两个只有一行实现的方法：甲只是把内部 Map 的 put 换成更长名称；乙表示“取消当前预订”，当前恰好只需更新一个内部字段。两者都应删除吗？

核对思路：不能仅按行数判断。要看调用者的理解是否更简单，以及内部表示变化能否被隔离。若乙明确表达业务动作和使用约束，调用者不必知道内部字段，未来表示改变也可留在方法内，它就可能有价值。甲若完整暴露原操作，却增加新名字的学习成本，就接近原书的浅方法例子。仍须检查乙有没有用短名称掩盖重要行为。
