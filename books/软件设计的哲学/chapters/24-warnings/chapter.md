# 《软件设计的哲学》警示信号总结｜从不顺手的地方找设计问题 · 书镜8.2

原则说明设计想达到什么，警示信号帮助我们发现哪里值得检查。看到一种信号，先确认它怎样增加当前任务的困难，再决定是否修改；信号不是自动裁决代码好坏的标签。

## 一、原书回顾：十四种需要留意的表现

原书这一总结单元没有编号小节。以下按原顺序保留全部信号及回查位置。

| 信号 | 具体可能出现什么问题 |
|---|---|
| 浅模块（4.5、13.5） | 学习接口的负担与它省下的工作差不多，封装没有隐藏多少细节。 |
| 过度暴露（5.1） | 为了完成普通任务，使用者也得了解很少用到的选项。 |
| 信息泄露（5.2） | 同一个设计决定反映在多个模块里，变化时要一起协调。 |
| 时序分解（5.3） | 只按执行先后划分代码，把需要共同维护的信息拆散。 |
| 直通方法（7.1） | 一个方法几乎只是把参数交给签名相似的另一个方法。 |
| 重复（9.3） | 相同代码片段散在多处，修改时容易遗漏或产生差异。 |
| 专用与通用混合（9.4） | 特定用途的要求进入通用机制，让其他使用者也必须面对。 |
| 连体方法（9.7） | 不理解另一个方法的实现，就难以理解或修改当前方法。 |
| 注释重复代码（13.2） | 注释只把可见操作再说一遍，没有补足需要了解的信息。 |
| 实现文档污染接口（13.5） | 接口说明堆满使用者并不需要知道的内部做法。 |
| 含糊的名称（14.3） | 名字没有精确说明变量、方法或对象表示什么。 |
| 难以取名（14.3） | 很难找到一个清楚名字，可能说明概念本身还没分清。 |
| 难以描述（15.3） | 必须用很长说明才能讲完整，可能有过多职责或条件。 |
| 不显而易见的代码（18.2） | 后来的人难以看出代码的行为、含义或需要遵守的规则。 |

这些信号与第2章的三种困难相连：要改很多地方、要了解很多事情，以及没有意识到还有事情需要知道。相同症状也可能有不同原因，需要回到具体代码中检查。

## 二、主题讲解：把警示转成可检查的问题

### 先问它造成了什么困难

假设一个方法名叫`handleData`。名字含糊是一个信号，但直接把它改成更长的名字，不一定解决问题。应先确认：它处理什么数据，做什么动作，会产生什么结果？若这几个问题无法用同一个职责解释，可能需要先理清方法的工作，再命名。

这个假设例子展示了警示的用法：从表面的名称问题，走到读者实际缺少的信息。不能只为了避开词表里的“含糊名称”，造一个更抽象、更长的名字。

### 同一个地方可能同时出现几种信号

一个保存接口要求十几个参数，还必须按隐藏顺序调用另外两个方法。它可能同时存在过度暴露、不显而易见和连体方法问题。可以先列出正确完成保存必须知道的事情，再看哪些能够由模块统一负责。

如果只是补上一份长文档，隐藏规则可能变得可见，但使用者仍需要记住很多步骤。文档和结构可以一起改；两者改善的是相关但不同的困难。

### 保留必要的例外

直通方法有时为了适配不同接口，或者维持一个有意义的边界而存在；浅模块也可能封装本来就简单的操作。读到信号后，应检查这层代码是否提供了必要的隔离或清楚的用法。

同样，两段代码看起来相似，不代表它们必须一起变化。贸然合并可能把不同业务要求绑在一起。应保留原书对应章节给出的条件，避免把警示表变成机械删除规则。

## 用一个变化检查理解

两个方法的实现几乎相同，一个用于普通订单，一个用于受监管订单。目前结果一样，但后者有独立的审核要求。是否应立即消除重复？

先判断它们是否表达同一规则、是否需要一起变化。可以共享确实相同的机制，同时保留各自的规则和入口。代码表面重复与业务决定重复，需要分开判断。
