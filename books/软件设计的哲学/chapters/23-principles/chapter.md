# 《软件设计的哲学》设计原则总结｜把原则用在一次修改上 · 书镜8.2

书末的原则表适合在读完正文后回查。它保留作者的判断方向，但每条原则成立的理由、例外和代价仍在对应章节中。不要仅凭表里的短句决定一次重构。

## 一、原书回顾：作者留下的十六条原则

这一部分是原书的总结单元，没有编号小节。下表依原顺序重述，括号内保留回查位置。

| 原则 | 用来提醒我们什么 |
|---|---|
| 1. 复杂性逐步累积（2.4） | 不断放过的小问题会影响越来越多的修改，日常细节也需要关注。 |
| 2. 能工作的代码还不够（3.2） | 完成当前功能时，也要考虑下一次理解和修改是否困难。 |
| 3. 持续作小额设计投入（3.3） | 随开发过程修正设计，避免把所有改进推迟到未来的大重构。 |
| 4. 模块应该深（4.4） | 用相对简单的接口承担有价值的复杂工作。 |
| 5. 让常见用法尽量简单（4.7） | 默认路径服务常见需求，特殊选项由需要它的人了解。 |
| 6. 重视接口的简单（第8章、9.7） | 不要只为实现者省一点事，让所有调用者承担更大的负担。 |
| 7. 通用模块往往更深（第6章） | 合适的通用操作可以覆盖多种用途，减少零散特例。 |
| 8. 分开通用代码和专用代码（6.6、9.4） | 不让某个用途的规则混进所有使用者都要面对的机制。 |
| 9. 不同层提供不同抽象（第7章） | 每一层都应有清楚的作用，避免只是原样转发另一层。 |
| 10. 把复杂性向下承担（第8章） | 能由下层可靠完成的工作，尽量不要反复交给上层使用者。 |
| 11. 通过定义减少不必要的错误情况（10.3） | 某些异常可以从接口语义上取消，而不是让每个调用者处理。 |
| 12. 设计两次（第11章） | 比较实质不同的方案，避免把第一个想到的方案当成唯一答案。 |
| 13. 注释说明代码中不明显的内容（第13章） | 写出必要的含义、原因和约定，不重复已经看得见的操作。 |
| 14. 为阅读者设计软件（18.2） | 写代码的人知道上下文，后来的人仍需要从代码获得足够信息。 |
| 15. 让开发推进抽象，而不只是堆功能（19.2） | 加特性时继续改善表达这些特性的结构。 |
| 16. 区分并强调重要信息（第21章） | 让关键概念容易被看到，让无关细节少占据使用者的注意力。 |

这些原则共同服务于减少复杂性。它们不是互不相关的十六项得分，也不是无条件的规定。原书前言已经要求读者用实际效果检验建议；第22章则回到长期投入和设计判断的成长。

## 二、主题讲解：不要一次套上十六条规则

### 从一个确实存在的困难开始

假设要给导出文件增加一个字段，现在需要同步修改五处拼接规则。先问五处是否表达同一项决定。如果是，就考虑集中这项决定；如果其中几处承担不同业务含义，就不能只因代码相似而合并。这个例子用于讲解，并非原书项目。

此时最相关的是信息隐藏、通用与专用的分离，以及模块职责。没有必要同时更换所有命名、设计异常框架和重新划分全部层次。原则帮助判断当前困难，不要求把每次修改扩成全面整改。

### 比较方案时同时看接口和内部

一种方案把五处规则收进一个方法，但要求调用者提供很多模式参数。另一种方案根据真实用途提供几个清楚的入口，并在内部共享相同的生成机制。

前者可能少了重复代码，却增加使用者需要记住的组合。后者可能保留更多方法，却更容易正确使用。应让两种方案处理同一个实际需求，比较必须知道的信息、修改位置和容易遗漏的条件。不能只按文件数或方法数选答案。

### 把结果连回原则，而不是用原则名字当证明

如果新方案让调用者少记一条清理规则，就能具体说明封装接走了什么。如果“简化”后必须读更长的参数说明，就需要检查复杂性是否只是转移到接口。

同样，定义某种错误不存在，前提是新的语义仍满足真实需求；通用化也要有真实的共同操作，不能为了想象中的未来增加大量选项。书中的“过犹不及”小节，就是防止原则被推到失去原意的位置。

## 用一个变化检查理解

重构后代码减少了，但新增一个选项需要修改统一处理器里的十个分支。这个模块是否因为“通用”就更好？

不能只看名称。需要判断它是否提供了稳定、清楚的通用操作，还是把许多不同用途压进同一个分支集合。真正减少的困难和新增的困难都要说明。
