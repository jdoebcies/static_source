第7章

不同层，不同抽象

第 6 章用通用操作隔开具体用途。本章检查另一种问题：代码虽然分了层，调用者却在每层遇到几乎相同的方法和参数。一个新层要有存在的理由，就应承担能让其他部分更简单的工作。

一、原书回顾：检查每一层增加了什么功能

作者在章首用两个系统说明“不同抽象”。文件系统上层处理可变长度文件的字节范围，中间层缓存固定大小的磁盘块，设备驱动再负责块在内存和二级存储之间的移动。网络协议的上层提供可靠字节流，下层尽力传送大小受限、可能丢失或乱序的数据包。每向下一层走，处理对象和承诺都有变化。

当相邻层提供相似抽象时，作者把它视为需要检查的分解问题。后文分别检查方法、装饰器、内部表示和跨层参数，而不是按层数多少直接评价系统。

7.1 直通方法

直通方法几乎只把参数交给另一个签名相同或相似的方法。原书编辑器的 TextDocument 有 15 个公有方法，其中 13 个属于这一类。例如 getLastTypedCharacter、getCursorOffset 和 insertString 都转到 TextArea；展示的第四个方法 willInsertString 只比转发多做了监听器是否为空的检查。

多出这一层，调用者要理解更多接口，但系统功能几乎没有增加。若 TextArea.insertString 的签名改变，TextDocument 也要跟着改。接口放在一个类、主要功能放在另一个类，还让开发者难以回答两个类各负责什么。原书把这列为“警示信号：直通方法”。

作者给出三种重新分工的可能：让调用者直接访问真正提供功能的低层类，移除高层对该功能的责任；在两类之间重新分配功能，使职责不再重叠；如果确实无法清楚分开，就合并类。原书图7.1依次展示原状态及这三种变化。

实际学生项目涉及 TextDocument、TextArea、TextDocumentListener 三个职责交织的类，后来通过移动方法合成两个类，消除了直通方法。这个结果说明需要检查整组职责，不能机械删除某一层后就宣称完成设计。

7.2 接口重复何时可行？

相同签名本身没有问题，重要的是各方法是否贡献有用的功能。调度器接收参数，依据它们从多个处理方法中选择一个，再把参数转交过去。它的价值在选择过程。Web 服务器可以根据 URL 匹配一组规则，决定读取静态文件，还是调用 PHP、JavaScript 等处理过程；转交的请求参数相同，不会抹掉这项职责。

另一情形是同一接口的不同实现，例如不同磁盘设备的驱动。它们提供相同操作，但各自解决不同设备的问题。这些实现通常处于同一层，并不相互转发；统一接口反而减少学习成本。判断接口重复时，要区分相邻层空转、具有选择职责的调度，以及同层的替代实现。

7.3 装饰器

装饰器，又称包装器，接收现有对象，提供相似或相同的 API，并扩展其功能。原书用 BufferedInputStream 说明：上层请求少量数据，缓冲对象从底层一次读取较大块，保存剩余内容供之后读取。另一个例子是为普通 Window 加水平、垂直滚动条的 ScrollableWindow。

装饰器有助于把特殊扩展与通用核心分开，但也容易为了很小的新功能引入一个类，并重复转发底层的大量接口。作者担心的是浅类不断增加，而不是否认缓冲本身的功能。合并 InputStream 与缓冲是作者针对书中设计的主张，不作为当前 Java API 的修改建议或使用规范。

创建装饰器前，作者要求考虑四条出路。较通用、与基类关系紧密、或大多数使用者都需要的功能，可以直接进入基类；仅服务某个场景的功能，可以留在该场景；多个相关的小扩展可以合进一个较深的装饰器；有的功能根本不必包住整个对象，例如滚动条也许能独立于窗口实现。

原书也保留适用情形：外部类的接口不能修改，而应用需要另一接口时，可以用包装类转换。本文沿用原书“装饰器”这一称呼，不借此扩展讨论其他模式分类。是否采用包装，仍要比较它真正提供的功能与增加的接口负担。

7.4 接口与实现

“不同抽象”也适用于一个类的内外。学生文本类内部按行存储，如果接口也只提供 getLine、putLine，上层插入字符或删除跨行范围时，就必须自己拆行、拼行。这些复杂代码散在不同界面操作里，文本类却只暴露了内部表示。

改成面向字符范围的接口后，insert 可以在任意位置插入包含换行符的字符串，delete 可以删除两个位置之间的文本；类内部仍可按行存储。拆分和拼接由文本类完成，外部才真正获得“修改文本范围”这一层抽象。内外的差异对应具体价值：调用者不必按存储方式组织操作。

7.5 直通变量

直通变量沿一长串调用传递，中间方法却不用它。原书例子中，命令行提供证书 cert，只有底层 m3 打开套接字需要它，main 到 m3 之间的 m1、m2 仍要在签名中带上它。以后增加证书等配置，沿途很多接口都要改。

作者依次比较三种替代方式。第一，把信息放进上下层已经共享的对象，省去逐层传值；但要继续追问这个共享对象如何到达底层，它本身可能也是直通变量。第二，用进程全局变量；这省掉参数，却可能使同一进程中两个独立系统实例互相冲突，而这种多实例情形在测试中很有用。

第三是作者常用的上下文对象：把某个系统实例的配置、共享子系统、性能计数器等共同状态集中起来，每个实例一个上下文。为了不让上下文再沿每次调用传递，主要对象在构造时取得并保存其引用。

图7-1｜依据原书图7.2的上下文方案重绘。左侧箭头表示运行调用，右侧箭头表示对象访问已保存的上下文；构造时的注入另行说明，不画成业务调用路径。

这样，新增一个配置通常不需要改动不使用它的中间方法签名；初始化和真正使用配置的地方仍需相应处理。全局状态集中后，也更容易识别、管理和在测试中调整。这里的“全局”是系统实例范围，一个进程可以拥有多个互不相同的上下文。

作者明确说这远非理想方案。上下文仍继承了全局变量的许多问题：字段为什么存在、在哪里使用可能不清楚，不加约束会形成巨大的数据杂物袋和隐蔽依赖；可变共享状态还可能引入线程安全问题。作者建议尽量使用不可变的上下文变量，并承认尚未找到更好的通用解法。这一保留必须与方案一起阅读，不能把上下文当作无条件的最佳实践。

7.6 结论

接口、参数、函数和类都需要开发者学习，因此每增加一个设计元素，就增加一份理解成本。它应消除至少足以抵偿这份成本的其他复杂性。相邻层重复抽象、直通方法和直通变量，都是收益可能不够的信号，需要回到具体功能判断。

二、主题讲解：沿一次调用，问每层替你解决了什么

先写出每层增加的可观察行为

下面是本文假设的文档服务。入口收到“删除一段文本”，经过 DocumentService 再调用 TextStore。如果两者都叫 delete(start, end)，而前者逐字转发，修改参数就得同时改两处，调用者没有获得额外保证。

换一种实现：DocumentService 检查文档是否可编辑，并把本次修改与其他相关操作组合成一个用户动作；TextStore 负责修改字符范围，即使底层按行存储也处理跨行拼接。两层现在承担不同工作。名称可以相似，差别要在真实行为中看见。不能为了让现有层显得有价值，临时想象尚未存在的校验、事务或日志。

选择删层、移功能还是保留，需要检查使用者

如果高层确实没有自己的工作，调用者直接使用 TextStore 可能最清楚。若高层有少量独立职责、部分功能又散在低层，应先把相同责任集中起来。若两个类始终一起变化、无法提供各自清楚的抽象，合并值得考虑。

若这个中间层按文档类型选择不同存储实现，它就和原书调度器相近：即使参数原样传递，也完成了选择。再比如两个 TextStore 实现分别处理不同存储方式，统一签名帮助替换它们。这些都说明，“一行调用”是线索，单靠行数还不能决定删除。

参数变少之后，还要检查依赖是否更难看见

继续这个假设：底层连接需要证书，若每个业务方法都带上 cert，接口显得与业务无关。构造连接对象时交给它一个系统实例的上下文，可以避免证书经过每次文本修改调用。

但若顺手把当前文档、用户选择、临时结果也塞进这个共享对象，对象就可能读到不属于本次操作的数据。原书方案针对实例级共同状态；每次请求都不同的数据有不同的生命周期，不能仅为减少参数而混入长期共享状态。这是依据本章风险作出的分析边界。

检查结果可以很具体：两套实例能否持有不同证书；中间业务方法是否仍需知道证书；真正使用证书的代码能否清楚找到其来源；字段是否可能在多线程间被修改。前三项避免传递或全局冲突，最后一项提醒上下文并未自动解决并发。

检验理解：相同签名是否一定是浅层

三个中间对象都提供 read(request)：甲只原样转发给固定对象；乙根据请求类型选择不同处理器；丙从底层批量取数据并缓存，满足后续小读取。应该优先检查哪个，另两个还需比较什么？

核对思路：甲最接近直通方法，检查有无真实职责及能否去掉或合并。乙有选择职责，丙有缓冲职责；它们的签名重复不意味着没有价值。但仍要检查规则是否集中、缓冲是否多数用途都需要，以及是否为少量扩展增加了过多包装方法。原书支持这种逐项比较，并未给出“包装层都删掉”的结论。
